# Risk Register

| # | Risk | Owner | Likelihood | Impact | Mitigation | Trigger to escalate |
|---|---|---|---|---|---|---|
| R1 | The client/API contract is incorrect even though the page renders, causing missing quote IDs or unreliable quote handling. | Front-End Team | M | H | Run `npm run type-check` after wiring changes and `npm test` in the API. Apply the provided `doc._id` mapper fix without weakening the contract. Verify API-backed IDs and save-and-reload behavior. | Type-check or API tests remain red before merge, or quote IDs are missing → route to the owning team and hold the merge. |
| R2 | Client estimates and API-calculated premiums drift, showing customers two prices for the same inputs. | Front-End Team + Platform Services Team | H | H | Follow the sponsor-approved rate instruction: the API is the source of truth. Align client base rates to auto `90`, home `135`, and life `70`. Verify auto/35/50000 shows **$450.00** in both the estimate and newly saved row. Leave historical seeded premiums unchanged. | Any newly saved quote disagrees with its estimate after alignment → escalate to the Delivery Management Team for sponsor confirmation; do not independently change rate policy. |
| R3 | The local demo environment becomes unavailable, or the wrong database is shown, leaving the showcase without usable quote data. | Platform Services Team | M | H | Use the local `evergreen` kind cluster rather than relying on cloud infrastructure. Confirm three API pods and one MongoDB pod are running. Save a demonstration quote into the cluster database, verify it survives reload, and prepare screenshot fallback. Document that VM and cluster databases are separate. | Thursday rehearsal or Friday readiness checks cannot load and persist quotes → escalate to the Delivery Management Team, reassess go/no-go, and activate screenshot fallback if unresolved. |
| R4 | The locally built API image is unavailable inside kind, preventing API pods from starting. | Platform Services Team | M | H | Build `evergreen-quote-api:2.0`, load it into the `evergreen` cluster, and follow the provided deployment sequence. Deploy MongoDB first and wait for availability before deploying the API. | API pods show `ImagePullBackOff` or `ErrImagePull` → verify the image tag and successful kind image load; escalate if the documented sequence does not resolve the issue. |
| R5 | Optional features or new stakeholder requests consume time needed for required integration, verification, and rehearsal. | Delivery Management Team | H | M | Prioritize required launch issues on the board. Keep renters coverage and other optional challenges separate. Assess new requests against the guide’s permitted edits, document tradeoffs, and obtain sponsor agreement before changing scope. | A request requires new application code or threatens Thursday’s merge or rehearsal → route it to the owning team and seek sponsor approval for deferral or reprioritization. |
| R6 | The API dev server, Docker container, and Kubernetes port-forward compete for port `3000`, disrupting connectivity or connecting the client to the wrong environment. | Platform Services Team | M | H | Run only one API endpoint on port `3000` at a time. Stop the dev server before starting the container, and stop the container before starting the cluster port-forward. Verify health and expected quote data before each demonstration. | An address-in-use error, failed quote load, or unexpected quote list appears → check the active port owner and database environment first; escalate if connectivity remains unavailable. |

**Scale:** L = Low, M = Medium, H = High.

## How I'll use this register

As the Delivery Manager, I will review this register at the start of each daily check-in and after each instructor inject. When a trigger fires, I will record the evidence, identify the affected environment, and move the issue to the top of the stakeholder status update.

I will route technical blockers to the owning team, track the next action, and seek sponsor decisions when scope or launch readiness is affected. I will update likelihood, impact, and mitigation as new evidence becomes available.

This register will remain committed in `delivery-leadership-package/risk-register.md` and support the go/no-go decision, Thursday rehearsal, and Friday showcase.
